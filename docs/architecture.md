# Architecture

## Repository layout

```
.
├── AGENTS.md                      rules and index for agents
├── CLAUDE.md                      redirect to AGENTS.md
├── README.md                      human overview and extension table
├── docs/                          this documentation (releases.md is the release runbook)
├── openspec/                      OpenSpec root for repository-wide changes
├── .changeset/                    release intents (<id>.md) and ledger (ledger.yaml), written by pnpm
├── .github/workflows/             ci.yml (checks, release-impact gate, artifact preflight) and release.yml (publication)
├── tools/
│   ├── e2e/                       end-to-end harness: a real Pi session with a scripted provider and recording UI
│   └── release/                   release checks and publication tooling: src/ and test/
├── .agents/skills/
│   ├── pi-extension-dev/SKILL.md  skill loaded when working on an extension
│   └── openspec-*/                OpenSpec workflow skills (generated by openspec init)
├── .claude/                       Claude Code commands and skills for OpenSpec (generated)
├── packages/
│   └── <name>/                    one Pi package per directory, published as @zeroclover/<name>
├── package.json                   workspace root (private): scripts and dev tooling only
├── pnpm-workspace.yaml            workspace members, build-script policy, versioning settings
├── tsconfig.base.json             shared strict compiler options
├── tsconfig.json                  typecheck entry covering packages/*/{src,test} and tools/*/{src,test}
├── biome.json                     lint and format rules
└── vitest.config.ts               test discovery (packages/*/test and tools/*/test), one process per file, timeouts
```

Agent-facing files follow one rule: `AGENTS.md` and `.agents/` are the shared, harness-neutral surface; `.claude/` is the only harness-specific directory, and `CLAUDE.md` contains nothing but `@AGENTS.md`. No other harness gets its own files.

The root never contains extension runtime code. It exists so that every package is checked by the same TypeScript, Biome, and Vitest configuration and so that the Pi host packages are installed once, giving the editor and `tsc` their type declarations and giving agents a local copy of Pi's docs and examples. `tools/` holds development and CI tooling under the same strict checks; nothing in it is published or loaded by Pi.

## Package anatomy

```
packages/<name>/
├── package.json        @zeroclover/<name>, version, description, pi manifest, peerDependencies, dependencies
├── README.md           what it does, how to install, tools/commands/config it provides
├── CHANGELOG.md        written by `pnpm version -r` from change intents, reviewed before commit
├── src/
│   ├── index.ts        extension entry: default export function (pi: ExtensionAPI)
│   └── *.ts            implementation modules, kept free of Pi API where possible
├── test/
│   └── *.test.ts       end-to-end scenarios through a real Pi session (tools/e2e), with package fixtures
└── openspec/           the package's own OpenSpec root: specs/ and changes/
```

Rules that follow from this layout:

- `src/index.ts` is the only file Pi loads. It wires registrations (`pi.registerTool`, `pi.registerCommand`, `pi.on`, ...) to implementation modules. Keep it thin so the wiring reads at a glance.
- Logic that does not need `ExtensionAPI` or `ExtensionContext` lives in separate modules under `src/`. Tests do not import them; they drive the extension through a Pi session (`docs/conventions.md`, "Tests").
- Relative imports use the `.ts` extension (`import { x } from "./x.ts"`). Pi loads sources through jiti and the compiler is configured with `allowImportingTsExtensions`.
- A package may contain skills, prompt templates, or themes next to its extension; declare them in the `pi` manifest.
- `openspec/` holds the package's specifications and change proposals. It is excluded from the published `files` and from the `pi` manifest; the OpenSpec CLI finds it as the nearest root when run from the package directory.

## OpenSpec roots

OpenSpec resolves its root by walking up from the working directory to the nearest `openspec/` directory. The repository uses two levels:

| Root | Covers |
|---|---|
| `openspec/` (repository root) | shared tooling, root docs, conventions, AGENTS.md |
| `packages/<name>/openspec/` | everything about that one extension |

Specs describe current behavior of the thing in their root, so a package's specs stay with the package: they move, publish, and get deleted with it, and the main repository root never accumulates specs for code it does not contain.

## Manifest and dependencies

```json
{
	"name": "@zeroclover/pi-<name>",
	"version": "0.1.0",
	"description": "One sentence, shown in package listings",
	"type": "module",
	"keywords": ["pi-package", "pi-extension"],
	"files": ["src", "README.md", "CHANGELOG.md"],
	"publishConfig": {
		"access": "public"
	},
	"pi": {
		"extensions": ["./src/index.ts"]
	},
	"peerDependencies": {
		"@earendil-works/pi-coding-agent": "*"
	}
}
```

- `name` is always `@zeroclover/<directory name>`; the directory, commit scope, and package OpenSpec root keep the bare name. The full `docs/workflow.md` template also carries the license and repository metadata.
- `files` lists plain paths and includes `CHANGELOG.md`; `pi` resource entries are plain paths inside `files`; `publishConfig.access` is `public` because scoped packages are private on npm by default. Versions change only through `pnpm version -r` (`docs/releases.md`).
- `pi.extensions` points at the entry explicitly. Pi also discovers a conventional `extensions/` directory, but an explicit manifest keeps `src/` as the single source layout.
- Host-provided packages are declared in `peerDependencies` with `"*"`: `@earendil-works/pi-coding-agent`, `@earendil-works/pi-ai`, `@earendil-works/pi-tui`, `@earendil-works/pi-agent-core`, `typebox`. List only the ones the package imports.
- Real runtime dependencies go in `dependencies` of the package, not the root. `pnpm install` at the root installs them through the workspace. Installed packages load with their own module root, so a package may not rely on another package's dependencies.
- The root `package.json` carries a `pi` manifest with the glob `./packages/*/src/index.ts` so that installing the whole repository from git loads every package; users narrow it with Pi's resource filters.

## Release records

Release state lives in committed files, never in CI: change intents in `.changeset/<id>.md`, each package's `CHANGELOG.md`, and the append-only ledger `.changeset/ledger.yaml` (`"<name>@<version>"` -> released directory and consumed intents). The release workflow publishes exactly the ledger records that a reviewed integration commit adds relative to its first parent, then writes the `<name>@<version>` tag and GitHub Release as output records. `docs/releases.md` has the procedure.

## How Pi loads a package

Pi reads `package.json`, resolves the `pi` manifest, and imports each extension entry with jiti. There is no build step and no `dist/`. The default export runs once per extension runtime; a `/reload` replaces the runtime. Because loading happens in-process, an extension has the same permissions as Pi itself.

The full contract (lifecycle, events, tools, state, UI, errors) is in Pi's own documentation; see `docs/pi-reference.md` for where to find it.
