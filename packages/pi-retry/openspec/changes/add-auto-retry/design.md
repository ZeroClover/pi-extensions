# Design

## Context

See proposal.md "Why" for motivation. Facts about Pi 1.2.0 that shape the design (verified in the Pi source, `packages/coding-agent/src/core/agent-session.ts` and `packages/agent/src/agent-loop.ts`, and in `node_modules/@earendil-works/pi-coding-agent/dist`):

- An error assistant message ends the agent-core loop at once: `finishTurn` (which dispatches the `turn_end` boundary) is called, but its `continue` decision is ignored for `error`/`aborted` messages and `agent_end` follows. Only `agent_before_settle` can request a continuation after a failure; `continue: true` there makes `AgentSession` call `agent.continue()` on the current context.
- `_handlePostAgentRun` runs Pi's own retry (`settings.retry`, pattern-based, `baseDelayMs × 2^(attempt−1)` capped at `maxAgentDelayMs`) and overflow compaction before `agent_before_settle`. The boundary fires with `outcome: "error"` only once Pi has given up on the message. Pi's retry omits its own failed attempts from the projection with a `context_edit` entry (`_omitRecoveryAttempt`); the last failure, the one Pi declined, is still in the projection.
- A boundary continuation is rejected (`agent_before_settle requested continuation without runnable model context`) when the last message in the projection is an assistant message. The boundary result may carry `context_edit` drafts, and Pi applies them before it checks `canContinue`.
- At `agent_before_settle` the agent has no active run, so `ctx.signal` is `undefined`. `AgentSession.abort()` (Escape, RPC `abort`) sets a flag that discards the continuation after the handler returns; it cannot interrupt the handler, and `_runBeforeSettleBoundary` commits the handler's `entries` *before* it checks that flag, so a result returned after an abort still appends its drafts. Extension commands run immediately while a session is busy, `ctx.hasPendingMessages()` reports queued user messages, and `ctx.ui.onTerminalInput()` lets an extension observe raw terminal input in interactive mode (a no-op elsewhere).
- `pi.getSettings()` returns the merged settings files without defaults, so an unset `retry.enabled` reads as `undefined`, not `true`.
- `after_provider_response` carries `{ status, headers }` and nothing that identifies the request. Whether it fires for an error response depends on the adapter (`packages/ai/src/api/*.ts`):

  | Adapter | Error-response headers via `after_provider_response` |
  |---|---|
  | Mistral (raw fetch), pi-messages (raw fetch), OpenAI Codex on its SSE transport only (the default `auto`/WebSocket path never calls `onResponse`), custom providers following the `streamSimple` contract | yes: `onResponse` runs before the status check |
  | Anthropic, OpenAI Completions, OpenAI Responses, Azure Responses (SDK + `retryProviderRequest`), Bedrock (deserialize middleware) | no: the SDK throws before `onResponse` |
  | Google Generative AI, Google Vertex, Gemini CLI | never: the adapter does not call `onResponse` |

  Error responses otherwise reach the extension only as `errorMessage` text and as diagnostics: Bedrock sets `details.status` and `details.errorCode` (the raw exception name, while the text gets Pi's prefixes `Throttling error:`, `Validation error:`, `Service unavailable:`, `Model stream error:`, `Internal server error:`); pi-messages sets `details.status` and `details.error` (the parsed provider error object with `code`, `type`, `message`; the text keeps only the message and the code), and `createAssistantMessageDiagnostic` puts the thrown exception's code at `diagnostic.error.code`; Codex sets no status. The same hook is also installed on prompt-cache warming requests (`sdk.ts` passes the agent's request options to `cacheWarmer.start`, and `cache-warmer.ts` replays `...run.options`; refreshes fire from a timer during the `streaming` phase as well as when idle, with `maxTokens: 1`), so a response event is not proof that a foreground request was made. Two events bracket what the extension can know: `context` fires only for the agent's own requests (Agent `transformContext`), immediately before the request; `cache_warming_decision` fires immediately before every warming request, whatever the final action. `pi.getSettings().cacheWarming` reports the mode (`off` disables warming).
- Built-in `/reload` is refused while `session.isStreaming`, which stays true through `agent_before_settle`; only a programmatic reload or shutdown delivers `session_shutdown` during a wait. `ctx.abort()` requests a run abort without awaiting idle; Pi then drops the boundary continuation and does not continue on queued messages.
- `message_start` receives a shallow copy of the assistant message (`agent-loop.ts`: `{ ...partialMessage }`); `message_end` receives the final object, which is what Pi persists and what the projection holds. Object identity is therefore usable only from `message_end` onward.
- Pi resets its own retry counter to zero once it gives up (`_handlePostAgentRun`, before `agent_before_settle`) and runs post-run recovery again after every extension continuation. With Pi's retry enabled, each pi-retry continuation can be followed by Pi's full retry sequence.
- `@earendil-works/pi-ai` exports `isContextOverflow`, `isRetryableAssistantError` and `retryDelayMs`; the first is reused, the other two inform the vocabulary but are not called (they encode Pi's policy, not this one).
- With `retry.provider.maxRetries > 0`, Pi's provider-level retry turns a `retry-after` above `retry.provider.maxRetryDelayMs` into the text `Server requested <n>s retry delay (max: <m>s)` (seconds rounded up), which this extension parses. This applies to the adapters wrapped in `retryProviderRequest` whose SDK errors carry headers (Anthropic, OpenAI Completions/Responses, Azure), not to Google, whose SDK errors have no headers. Users of those adapters can set `retry.provider.maxRetries: 1` and `retry.provider.maxRetryDelayMs: 1` to surface the header as text; the README documents this as optional and the design does not depend on it.
- Repository rules: `src/index.ts` is thin wiring, logic lives in modules with Vitest tests, no timers in the factory, no `console`, host packages as peer dependencies, configuration under `getAgentDir()` as pi-tps does.

## Goals / Non-Goals

**Goals:**
- One decision function, pure and table-driven, that every retry goes through and that tests can exercise with real provider error strings.
- Correct behaviour in every Pi mode and when other extensions also use `agent_before_settle`.
- Honest handling of what Pi exposes: headers when they exist, text otherwise, and no guessing of a provider's intent when neither says anything.

**Non-Goals:**
- Replacing or configuring Pi's built-in retry or provider-level retry.
- Switching models or providers on failure (virtual models cover that).
- Retrying compaction, branch summaries, tool executions, or nested `streamSimple` calls made by other extensions.
- Persisting retry state across sessions.

## Decisions

### D1. Integrate at `agent_before_settle`, after Pi's own retry

The handler runs when `event.outcome === "error"`, `event.continue` is false, and the last projected message is an error assistant message. Alternatives: (a) `turn_end` — its continuation is ignored for error messages (see Context); (b) rewriting `errorMessage` in `message_end` so Pi's regex accepts it — gives no control over the delay, cannot honour a 5-minute retry-after, and depends on Pi's wording; (c) `pi.sendMessage(..., { triggerTurn: true })` from a timer after settlement — starts a new run with a custom message the model sees, breaks `agent_settled` semantics for RPC clients, and leaves a timer running outside any session event. (a) and (b) are rejected on correctness, (c) on cleanliness. Pi's retry is not disabled by the extension (it cannot be). Because Pi renews its budget before every extension continuation, leaving it enabled multiplies attempts (up to (maxRetries + 1) × (Pi maxRetries + 1)) and lets Pi's fixed delays run before each hint-aware wait; the layering is explained once per session (retry-controls spec) and the README states that disabling Pi's retry is required for pi-retry to govern timing.

### D2. Hide the failed attempt with a `context_edit` draft

The result returns `{ entries: [...event.entries, { type: "context_edit", targetId, replacement: null }, { type: "custom", customType: "pi-retry", data }], continue: true }`. Pi's boundary runner replaces the accumulated drafts with a handler's `entries` (`runner.ts`: `entries = handlerResult.entries`), so the drafts of earlier handlers must be carried forward explicitly. `targetId` is found by walking `event.context.contextEntries` from the end for the first entry whose `sourceEntry` is a message entry with an assistant message of stop reason `error`; its `messages` array is non-empty because Pi has not omitted it. This mirrors `_omitRecoveryAttempt` and keeps the failed message in the session file for inspection. If no such entry is found, the handler reports an extension error and returns nothing rather than continuing with an assistant message at the tail. The custom entry is a session record outside model context: `{ attempt, category, reason, delayMs, hintSource?, provider, model }`.

### D3. Classification as ordered rules

`classify(input): Classification` where `input = { text, status?, headers?, diagnostics?, patterns }` and `Classification = { category, retryable, reason, hint? }`. Evaluation order:

1. User `nonRetryable` patterns → not retryable, category from the built-in rules or `unknown`.
2. User `retryable` patterns → retryable, same category rule.
3. Context overflow via `isContextOverflow(message)` (the whole `AssistantMessage`, since it checks the provider) → `context_overflow`, not retryable (Pi's compaction owns it; by the time the boundary fires Pi has already decided not to compact). Skipped when the recognised status is 429 or 529 or a `rate_limit` / `overloaded` word rule matches: Pi's overflow patterns include `too many tokens` and `token limit exceeded`, which throttling messages also use.
4. Status recognition: captured `status` (error captures only), then `diagnostics[].details.status`, then the guarded text match restricted to the mapped error codes (spec "HTTP status recognition"). A 5xx status whose body carries `"code": 429` or `RESOURCE_EXHAUSTED` counts as 429 (LiteLLM's gateway-envelope rule). Diagnostic values `details.errorCode`, `details.error.code`, `details.error.type` and `error.code` are appended to the text the word rules see, so a deterministic type that Pi left out of the rendered text (pi-messages' `error.type`) still classifies. The status is recorded; it is applied in steps 6 and 8.
5. Deterministic word rules in order `context_overflow` (wording `isContextOverflow` does not know, such as `ContextWindowExceededError`, `request_too_large`), `auth`, `not_found`, `content_policy`, `invalid_request`, `quota`. A word match for `invalid_request` is discarded when the recognised status is 408, 409, 429 or 5xx (OpenAI 429 bodies say `invalid_request_error` for some limits; LiteLLM maps on the status first).
6. Specific statuses → their category: 4xx deterministic codes (400, 401, 402, 403, 404, 413, 422), 408/504/524 → `timeout`, 409/429 → `rate_limit`, 529 → `overloaded`. A 400 therefore beats transient words, so a 400 whose echoed prompt mentions "rate limit" stays `invalid_request`.
7. Transient word rules in order `rate_limit`, `overloaded`, `timeout`, `transport`, `server_error`.
8. Any other 5xx status → `server_error`. Applied after the word rules so that `503 The model is overloaded` is `overloaded` and `500 ThrottlingException` is `rate_limit`.
9. Nothing matched → `unknown`, retryable.

Steps 1 and 2 record the override; they do not short-circuit, so the category is still computed. Then the hint is extracted (D4) and the final decision is resolved in one place, first match wins: hint above `maxRetryAfterMs` → not retryable; `nonRetryable` override → not retryable; `retryable` override → retryable; built-in rule (`quota` retryable only with an accepted hint, deterministic categories never, the rest always). Status 402 and the `PaymentRequiredError` / `Payment Required` wording are `quota`. The rule tables are plain arrays of `{ pattern: RegExp, category }` in `src/vocabulary.ts` with a source comment per group (Pi, LiteLLM, provider docs), so the vocabulary is reviewable and testable in isolation. "quota" is deliberately narrower than Pi's non-retryable list: Google's `Quota exceeded for quota metric 'Generate requests per minute'` is a per-minute limit that resets, so `quota exceeded` alone is `rate_limit`, while `insufficient_quota`, `billing`, `out of budget`, `BudgetExceededError`, `PaymentRequiredError`, `Payment Required`, `exceeded your current quota` and subscription limits are `quota`.

Alternative considered: a single retryable/non-retryable regex pair like Pi. Rejected: no categories means no explanation, no per-category rules (quota with hint), and no way to review provider coverage.

### D4. Hint extraction with three sources and one lifecycle

`extractHint({ headers?, diagnostics?, text, now }): Hint | undefined` with `Hint = { delayMs, source }`, trying headers, then diagnostics, then text, in the orders the retry-hints spec lists. `retry-after(-ms)` is read for every error status; the window-reset headers (`x-ratelimit-reset-*`, `anthropic-ratelimit-*-reset`, `ratelimit-reset`) describe quota windows and are read only for a 429, so a 503 with routine window headers does not turn into a long wait. Unit parsing is shared: durations (`1.5s`, `6m0s`, `250ms`, `12 minutes`, `2 hours`), HTTP-dates, RFC 3339, and epochs with the 10^9/10^12 thresholds. The clock is injected for tests.

Capture lifecycle (`src/capture.ts`): Pi gives no way to correlate a response event with a request, so attribution is not inferred; it is *gated* on conditions under which one foreground request provably yields one response event. The gate is open only when `pi.getSettings().cacheWarming === "off"` and no `cache_warming_decision` has fired in the session (no warming requests share the hook), `retry.provider.maxRetries` is 0 (no provider-level attempts inside one call; Pi's default), and the failed message's `api` is not `openai-codex-responses` (its own `DEFAULT_MAX_RETRIES` loop calls `onResponse` per attempt). With the gate open, a window runs from the failed request's `context` event (agent-only) to its assistant `message_end` and must hold exactly one capture with status ≥ 400; anything else yields no header hint, and a second capture closes the gate for the session as evidence the assumptions do not hold. With the gate closed (Pi's defaults), header hints are simply off and diagnostics and text apply; `/retry` shows the gate state and reason, and the README explains which settings open it. Alternatives rejected: clearing uncertainty at message or run boundaries (a warming request can outlive them), last-event-wins (a 429 → 200 → mid-stream failure sequence or a 429 followed by a retry that fails before headers both inherit a wrong hint). Codex text hints (`Try again in ~N min.`) are parsed from the friendly message Pi throws, since the raw `resets_at` field does not survive the adapter.

### D5. The wait runs inside the handler, in one-second slices

`waitFor(delayMs, { shouldStop: () => "cancel" | "proceed" | undefined, onTick })` loops over `setTimeout` slices of at most 1 s. Each tick updates the status line and asks `shouldStop`, which the controller implements as: cancelled by `/retry cancel`, `/retry off` or Escape → `"cancel"`; `ctx.hasPendingMessages()` → `"proceed"` only when the wait is a backoff wait. Every cancel also calls `ctx.abort()` before the handler returns `undefined`: without it Pi would still continue on queued messages (`_runBeforeSettleBoundary` continues when `result.continue || hasQueuedMessages()`), sending a request before a retained provider deadline. The abort flag makes Pi drop both. A wait that honours a provider hint keeps its deadline; the queued message is delivered with the retry at the deadline, because sending early would violate the wait the provider asked for. Timers are created only inside the handler and always cleared, satisfying the "no timers in the factory" rule. Three more stop sources: in interactive mode the handler subscribes to `ctx.ui.onTerminalInput` for the duration of the wait and treats an Escape key (`matchesKey(data, "escape")` from `@earendil-works/pi-tui`, added as a peer dependency) as `"cancel"`, so the common abort gesture ends the wait within a second and the handler returns `undefined` (no drafts, no continuation); `session_shutdown`, `session_before_switch` and `session_before_fork` handlers cancel any wait: session replacement awaits `session.abort()` (which awaits idle) *before* it emits `session_shutdown`, so only the `before_*` events fire early enough to keep a switch from waiting out the delay (the built-in `/reload` command is refused while the session is busy, so the README says: cancel first, then reload); `agent_settled` with `aborted: true` resets the controller. An abort that the extension cannot observe (RPC `abort`) still lets the wait finish; Pi then commits the drafts and discards the continuation (Context), which omits an error message that carries no content and leaves a `pi-retry` entry whose outcome the `agent_settled` handler rewrites to `cancelled` by appending a follow-up entry (`pi.appendEntry`). The README states that Escape, `/retry cancel` or a typed message end a wait. Alternative considered: waiting outside the handler with a timer and a custom-message trigger; rejected in D1.

### D6. Controller state

`RetryController` (`src/controller.ts`) holds `attempt`, `enabledForSession`, `waiting?: { attempt, endsAt, reason, cancel() }` and the capture. It is created in the factory (plain object, no resources), reset on `session_start` with the freshly parsed configuration, and exposed to the command. `message_end` with an assistant message whose stop reason is neither `error` nor `aborted` resets `attempt` and reports success when a retry was in flight; an `aborted` message resets silently (Pi's own `retryAssistantCall` treats aborts the same way); `before_agent_start` and `agent_settled` with `aborted: true` reset `attempt`. The layering notice checks `pi.getSettings().retry?.enabled !== false`. The handler is the only writer of `waiting`.

### D7. Configuration

`src/config.ts` follows pi-tps: `parseConfig(text | undefined, source) → { config, warnings }`, defaults in one function, one warning per problem, unknown keys warned, ranges from the retry-configuration spec. User patterns are compiled with the `i` flag; a pattern that throws is dropped with a warning. The file is read in `session_start` (not in the factory) with `node:fs/promises`.

### D8. Modules and tests

| Module | Responsibility | Tests |
|---|---|---|
| `src/vocabulary.ts` | rule tables per category with source comments | covered through classify tests |
| `src/classify.ts` | status recognition, rule evaluation, overflow guard, final decision | table-driven: ≥ 40 real error strings from Pi's retry/overflow tests, LiteLLM's exception mapping and provider docs, each with expected category and decision; 5xx-with-transient-words rows; throttling-with-tokens rows |
| `src/hints.ts` | header, diagnostic and text hint extraction, unit parsing, acceptance limit | each header and text form from the spec, past/garbage values, limit edge cases |
| `src/backoff.ts` | delay computation with injected random | sequence and cap, hint plus grace |
| `src/wait.ts` | sliced wait with stop callback and tick | fake timers: cancel, proceed, completion, tick cadence |
| `src/capture.ts` | header-capture gate and window | gate open/closed per condition, single-capture window, second capture closes the gate, stale capture |
| `src/controller.ts` | attempt budget, enabled flag, waiting state, decision glue | budget, resets, reasons |
| `src/config.ts` | file parsing and validation | per-field fallbacks |
| `src/index.ts` | registrations only (`session_start`, `session_shutdown`, `session_before_switch`, `session_before_fork`, `context`, `cache_warming_decision`, `after_provider_response`, `message_end`, `before_agent_start`, `agent_before_settle`, `agent_settled`, `/retry`) | load smoke test |

### D9. Reporting

Notifications use the exact strings in the retry-controls spec so RPC clients can match them. `ctx.ui.notify` and `setStatus` are no-ops in JSON and print modes (Pi's runner supplies a no-op UI there); the `pi-retry` custom entry is the machine-readable record in every mode and appears in the JSON/RPC event stream as `entry_appended`. The status line uses key `pi-retry`. No custom components, no widgets, no theme use.

## Risks / Trade-offs

- [Headers are invisible for the SDK adapters and Google, so most Anthropic/OpenAI/Google 429s carry no header hint] → Text hints cover OpenAI and Google (`retryDelay`); Anthropic 429s fall back to backoff (2 s … 60 s), which still succeeds for short limits; the README carries the adapter table and the optional provider-retry setting for the SDK adapters. A future Pi version that fires `after_provider_response` for error responses is picked up without code changes.
- [Response events cannot be correlated to requests, so header hints are off under Pi's defaults] → The gate makes misattribution impossible rather than unlikely; text and diagnostic hints cover OpenAI, Google, Codex and Pi's cap message; users of raw-fetch adapters open the gate with `cacheWarming: off`.
- [Unknown errors are retried, so a deterministic failure with unfamiliar wording is retried `maxRetries` times] → Deterministic vocabulary is broad (status codes, LiteLLM class names, provider error types), the user can add `nonRetryable` patterns, and every retry is visible with its reason; the cost is bounded by `maxRetries` and `maxBackoffMs`.
- [An abort the extension cannot observe (RPC `abort`) does not interrupt a long wait, and Pi commits the drafts anyway] → Escape in the terminal, `/retry cancel`, `/retry off`, queued messages (backoff waits) and shutdown end the wait within a second, and every cancel aborts the run so queued messages cannot trigger an early request; the committed omission hides only an empty error message; the `pi-retry` record is corrected to `cancelled`; a wait is never longer than the accepted hint or `maxBackoffMs`.
- [Pi's own retry runs first with its own delays when left enabled, and renews its budget before every pi-retry continuation] → Worst case with defaults is 44 requests (11 × 4); documented, with the statement that disabling Pi's retry is required for pi-retry to govern every attempt; pi-retry's `maxRetries` counts its own continuations only.
- [Another extension's boundary drafts are lost because Pi replaces, not appends, `entries`] → The result always starts with `event.entries`; the target entry is looked up from `event.context`, which already reflects those drafts.
- [Regular-expression false positives on bare status codes in error bodies] → Guarded status recognition (spec) and tests with token-count strings from LiteLLM's #11455 case.
- [Clock skew makes an absolute reset time look past or far future] → A past time yields no hint (backoff), a far-future one hits `maxRetryAfterMs` and is reported with the computed duration, so the user sees the provider's value.

## Open Questions

None that affect the specs or the task breakdown. Default values (`maxRetries` 10, `baseDelayMs` 2000, `maxBackoffMs` 60 000, `maxRetryAfterMs` 30 min) are recorded as assumptions in the retry-configuration spec and are trivially adjustable in the file.
